# 레포 분석 가이드: DNA 추출 방법

## 1. 철학 (Philosophy) 추출

### 소스
- README.md: 프로젝트 소개, "why" 섹션, 비전/미션
- CONTRIBUTING.md: 기여 원칙, 코드 리뷰 기준
- CLAUDE.md / AGENTS.md: AI 에이전트에게 주는 지시 (프로젝트의 가치관이 가장 명확히 드러남)
- 코드 주석, 변수명, 함수명: 암묵적 가치 (예: `safeguard`, `validate` → 안전 중시)

### 추출 기준

| 항목 | 질문 | 근거 찾을 곳 |
|------|------|-------------|
| 핵심 가치 | 이 프로젝트가 가장 중요하게 여기는 것은? | README 첫 문단, "Philosophy" 섹션 |
| 에이전트 관점 | 에이전트를 어떻게 정의하는가? | 에이전트 설정, 역할 정의 |
| 사람-에이전트 관계 | 누가 주도하는가? | 승인 플로우, 자동화 수준 |
| 자율성 수준 | 얼마나 자율적 행동을 허용하는가? | 가드레일, 제한 설정 |
| 설계 신념 | "~보다 ~가 중요하다" 형태의 원칙은? | 설계 문서, PR 토론 |

### 주의사항
- README에 명시된 것만이 아니라, 코드 구조에서 **암묵적으로** 드러나는 가치도 추출한다
- 추측이 아닌 근거(실제 인용)를 반드시 포함한다

## 2. 아키텍처 패턴 (Patterns) 추출

### 5개 카테고리별 탐색 가이드

#### 오케스트레이션 (Orchestration)
- **뭘 찾나**: 에이전트/태스크가 어떻게 조율되는가
- **어디서**: 메인 진입점, 에이전트 디스패처, 태스크 큐
- **패턴 후보**: Hub-and-spoke, Pipeline, Event-driven, Blackboard, Hierarchical

#### 라우팅 & 모델 선택 (Routing)
- **뭘 찾나**: 어떤 모델/에이전트에게 어떤 작업을 보내는가
- **어디서**: 모델 설정, 에이전트 선택 로직, complexity 판정
- **패턴 후보**: Complexity-based, Role-based, Fixed, Dynamic, Cost-optimized

#### 상태 관리 (State Management)
- **뭘 찾나**: 대화/작업 상태를 어떻게 저장하고 전달하는가
- **어디서**: state 파일, context 관리, 세션 스토리지
- **패턴 후보**: File-based, In-memory, Event-sourced, Shared-context, Hierarchical

#### 에러 처리 (Error Handling)
- **뭘 찾나**: 실패 시 어떻게 대응하는가
- **어디서**: catch/try 블록, fallback 로직, retry 패턴
- **패턴 후보**: Retry-with-backoff, Graceful-degradation, Fail-fast, Human-escalation, Self-healing

#### 컨텍스트 관리 (Context Management)
- **뭘 찾나**: LLM 컨텍스트 윈도우를 어떻게 관리하는가
- **어디서**: 프롬프트 조합, 컨텍스트 압축, 메모리 시스템
- **패턴 후보**: Sliding-window, Summarization, Hierarchical, RAG-augmented, Selective-injection

### 각 패턴 기술 형식
```
- **패턴명**: [정확한 이름]
- **설명**: [1-2문장으로 어떻게 작동하는가]
- **구현**: [파일 경로 + 핵심 메커니즘]
- **연결 철학**: [어떤 가치/신념에서 이 패턴이 나왔는가]
```

### 주의사항
- 모든 카테고리에 패턴이 있을 필요는 없다. 해당 없으면 "해당 없음 — [이유]"
- "기타 주목할 패턴" 섹션에서 5개 카테고리 밖의 독특한 패턴을 포착한다
- 프롬프트 중심 프로젝트의 경우: 프롬프트 체이닝, 템플릿 구조 등도 "패턴"으로 본다

## 3. 기능 맵 (Feature Map) 추출

### 기능 발견 소스
- 에이전트/스킬 정의 파일
- CLI 명령어 목록
- 설정 옵션
- 플러그인/확장 시스템
- README의 "Features" 섹션

### 매핑 규칙
- 각 기능은 반드시 **카테고리** (orchestration/routing/state/ui/tool 등)에 배정
- 각 기능은 가능하면 **기반 패턴**과 **기반 철학**에 교차 링크
- **성숙도 판정**: 실험적(문서 부족, API 불안정) / 안정(문서 있음, 테스트 있음) / 핵심(프로젝트 정체성)

## 4. 한계 & 트레이드오프 추출

### 트레이드오프 발견 소스
- 이슈 (특히 won't fix, by design 레이블)
- PR 토론 (거절된 PR이 특히 유용)
- README의 "Limitations" / "Non-goals" 섹션
- 다른 프로젝트와의 기능 비교

### 분석 관점
| 관점 | 질문 |
|------|------|
| 의도적 선택 | 이 프로젝트가 의도적으로 포기한 것은? |
| 구조적 한계 | 현재 아키텍처로는 불가능한 것은? |
| 스케일링 | 규모가 커지면 문제될 부분은? |
| 진화 방향 | 저자가 향후 어떤 방향을 계획하는가? |

### 주의사항
- 한계를 지적하되 **근거**를 포함한다 (추측 금지)
- "경쟁 프로젝트 대비 약점"은 실제 비교 대상이 분석되어 있을 때만 작성한다
