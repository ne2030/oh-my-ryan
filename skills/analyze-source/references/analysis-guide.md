# 분석 가이드: 요약, 계층화, 검증, 평가

> v2 부터 평가 루브릭이 **범용화**되었다. "실행 가능성" 같은 하네스 특화 항목은 제거되고, 트랙별 특색은 **트랙 delta 섹션**(`하네스 적용 제안` / `기술 의미` / `도입 조건`)으로 이동했다.

## 1. 원본 요약 작성법

3-5문장으로 작성하되, 아래 4요소를 반드시 포함한다:

| 요소 | 설명 | 예시 |
|------|------|------|
| **누가** | 저자 + 맥락 (직책, 소속) | "채널톡의 AI Native Engineer인 Park이" |
| **무엇을** | 핵심 주장 또는 경험 | "6개월간 코드 0줄로 560개 PR을 머지한 경험을 공유한다" |
| **핵심 근거** | 주장을 뒷받침하는 가장 강력한 데이터/논거 1-2개 | "105K줄 테스트, CI 10분→2분 단축" |
| **결론/시사점** | so what? 이것이 왜 중요한가 | "AI Native 레포를 만드는 것은 좋은 엔지니어링 그 자체다" |

**금지 사항**:
- "~에 대해 이야기한다" 같은 메타 서술로 끝내지 않기
- 저자의 결론을 반드시 포함할 것 (요약만 하고 결론 누락 금지)

## 2. 인사이트 계층화 기준

### 원칙 (Principles) — "다른 맥락에서도 성립하는가?"

- **판별**: 소스의 구체적 맥락(회사, 기술, 시점)을 제거해도 여전히 유효한 명제
- **형태**: "~하면 ~한다" 또는 "~보다 ~가 중요하다" 형태의 일반 법칙
- **예**: "시스템이 AI 실수를 잡으면 사람 개입이 줄어든다" → 채널톡이 아니라 어디서든 성립
- **개수**: 2-4개. 너무 많으면 추상화가 부족한 것

### 사례 (Cases) — "구체적 수치/결과가 있는가?"

- **판별**: 특정 맥락에 종속된 구체적 적용 결과
- **필수 포함**: 수치, 기간, 규모, 결과 중 최소 1개
- **형태**: "[주체]가 [행동]하여 [결과]를 달성" 형태
- **예**: "22개 레포에서 560+ PR, 최대 10개 동시 작업" → 채널톡의 구체적 수치
- **개수**: 3-6개. 소스 내 주요 데이터 포인트를 모두 포착

### 프레임 (Frames) — "기존 사고방식을 깨는가?"

- **판별**: 기존 가정 A를 새로운 관점 B로 전환하는 명제
- **필수 형태**: "A → B" (기존 → 새로운) 전환 구조
- **원칙과의 차이**: 원칙은 "무엇이 참인가"를 말하고, 프레임은 "무엇이 바뀌었는가"를 말한다
- **예**: "코드 작성자 → 의사결정자" → 역할의 전환을 표현
- **개수**: 1-3개. 없을 수도 있음

### 경계가 모호할 때

| 상황 | 판정 |
|------|------|
| 맥락 제거해도 성립 + 전환 구조 없음 | 원칙 |
| 맥락 제거해도 성립 + "A→B" 전환 구조 있음 | 프레임 |
| 구체적 수치/결과 포함 | 사례 |
| 동일 내용이 원칙이자 프레임 같음 | 프레임 우선 (전환이 더 강한 인사이트) |

## 3. 검증 방법 (B 깊이)

### 3.1 내부 근거 추출

소스 텍스트에서 아래를 테이블로 정리한다:

| 추출 대상 | 설명 |
|-----------|------|
| 정량 데이터 | 숫자, 비율, 기간, 금액 |
| 구체적 사례 | 실제 적용 결과, 전후 비교 |
| 논리 체인 | "A이므로 B, B이므로 C" 형태의 추론 |

### 3.2 외부 검증 — URL 필수

검증한 내용에는 **반드시 출처 URL 또는 출처명을 명시**한다. "확인됨"이라고만 쓰지 않는다.

트랙별로 우선 검증 대상이 다르다:

| 트랙 | 우선 검증 대상 | 출처 표기 예시 |
|---|---|---|
| `harness` | 제품·도구·스킬 실존, 저자 신뢰성 | `LinkedIn 프로필 (URL)`, `GitHub 레포 (URL)` |
| `model` | 논문 arXiv ID, 코드 공개, 벤치마크 1차 출처 | `arXiv:2602.08234`, `paperswithcode.com/...` |
| `ax` | 조직·기업 실재, 공시/IR 데이터, 사례 대표성 | `Workday FY2026 Q3 Earnings (URL)`, `채용공고 (URL)` |

공통 검증 항목:

| 검증 대상 | 방법 |
|-----------|------|
| **저자/기업 프로필** | LinkedIn, 기업 웹사이트 확인 |
| **재무 데이터** | 실적 발표, IR 자료, 뉴스 기사 |
| **제품/기술 존재 여부** | 공식 문서, 릴리즈 노트 |
| **주장의 합리성** | 업계 벤치마크, 유사 사례 대조 (상식적 범위 판단은 URL 불필요) |

### 3.3 검증 불가 시

검증할 수 없는 주장은 **명시적으로 "미검증"으로 표기**한다:
```
- **[주장 내용]**: 미검증. [검증 불가 사유: 비공개 데이터 / 개인 경험 / 출처 불명]
```

## 4. 검증 방법 (C 깊이 — B에 추가)

B의 모든 검증 수행 후 추가로:

### 4.1 관련 자료 탐색
- WebSearch로 핵심 키워드 검색 (최소 3회)
- 검색어 예: "[핵심개념] research", "[저자명] [주제]", "[기술명] benchmark"
- `model` 트랙이라면 context7로 기술 문서 참조 권장

### 4.2 지지/반박 자료 수집
- 동일 주장을 지지하는 다른 출처 최소 1개
- 반박하거나 다른 관점을 제시하는 출처 최소 1개 (있는 경우)
- 각 자료: `[제목](URL) — 1문장 요약` 형태

### 4.3 확장된 맥락
- 이 소스가 속한 더 큰 담론/트렌드는 무엇인가
- 시간축에서 이 소스의 위치 (선행 연구 → 이 소스 → 후속 발전)

## 5. 분석자 코멘트

"관련 노트" 앞, "근거 및 출처" 뒤에 `## 분석자 코멘트` 섹션을 작성한다. 이 섹션은 **트랙 무관 공통**이다.

### 5.1 논리 평가

이 글의 논증 구조를 평가한다:

- **논증 구조**: 주장 → 근거 → 결론의 흐름이 명확한가?
- **약한 고리**: 논리적 비약, 근거 없는 일반화, 생존자 편향 등이 있는가?
- **설득력**: 1-5점 (1=주장만, 5=데이터+논리+반론 고려)

### 5.2 신뢰도 판정

검증 결과를 종합하여 판정한다:

| 등급 | 기준 |
|------|------|
| **높음** | 핵심 주장의 80%+ 외부 검증 가능, 저자 신뢰성 확인 |
| **중간** | 일부 검증 가능, 일부 미검증이나 합리적 범위 |
| **낮음** | 대부분 미검증, 또는 검증 결과 사실과 불일치 |

A깊이에서는 "신뢰도 판정 불가 — A깊이"로 표기.

### 5.3 확장 설명

소스에서 사용된 개념/용어 중 추가 설명이 가치 있는 것을 골라 풀어 설명한다. 모든 개념을 설명하지 않는다. 핵심 인사이트 이해에 필요한 것만 선별.

### 5.4 비판적 관점

이 글이 놓친 것, 반대 의견, 한계를 제시한다.

**근거 필수 원칙 — 비판에도 동일하게 적용**:
- 수치를 인용하면 **반드시 출처를 명시**한다
- 출처를 찾을 수 없는 수치는 사용하지 않고 논리적 근거로 비판한다
- "~로 알려져 있다" 같은 표현도 근거 없이 쓰지 않는다
- **비판의 신뢰도는 비판 대상보다 높아야 한다**

## 6. 트랙 delta 섹션

트랙별로 **분석자 코멘트 뒤, 관련 노트 앞**에 트랙 전용 섹션을 추가한다.

### `harness` → "하네스 적용 제안"

**언제 작성**: 글에 하네스(스킬·에이전트·워크플로우)에 이식 가능한 패턴/기법이 있을 때만.

**작성 기준**:
- 하네스의 현재 구체화 수준에 맞춰 작성 (초기: 방향 제시, 구체화 후: 모듈/기능 지정)
- "적용 가능할 수 있다" 같은 모호한 제안 금지
- 적용 영역 + 구체적 방향 + 소스 참조를 반드시 포함
- 해당하지 않으면 섹션 자체를 비워둔다 (억지 연결 금지)

**형식**:
```
- **적용 영역**: [ryan-lab의 어느 스킬/구성요소]
- **방향**: [구체적 변경안]
- **참고**: [[소스 노트 wikilink]] — "인용"
```

### `model` → "기술 의미"

**언제 작성**: 모델·알고리즘·아키텍처 관련 글에서 "이 기법이 모델 역량의 무엇을 바꾸는가"를 짚을 수 있을 때.

**작성 기준**:
- 단순 요약이 아니라 "능력의 어느 축을 바꾸는가" 를 명시
- 선행 연구 대비 기여도 (점진적 개선 / 새 축 개척 / 기존 한계 돌파)
- 재현 가능성 (오픈소스·체크포인트·데이터 공개 여부)
- 벤치마크 일반화 가능성 (단일 벤치마크 편향 경계)

**형식**:
```
- **기여의 축**: [추론 능력 / 효율 / 안전성 / 일반화 ...]
- **선행 대비 기여**: [구체적 기여 + 수치]
- **재현 가능성**: [공개 여부 + URL]
- **한계**: [일반화 경계]
```

### `ax` → "도입 조건"

**언제 작성**: 조직·프로덕트·실무의 AI 도입/변화를 다룬 글.

**작성 기준**:
- 이 변화가 **성립하는 조직 전제** (규모, 문화, 자원, 리더십)
- 이 변화가 **성립하지 않는 조건** (저항 요인, 실패 패턴)
- 1차 효과 vs 2차 효과 분리
- N=1 케이스에 대한 일반화 경계 명시

**형식**:
```
- **성립 조건**: [이 변화가 작동하려면 필요한 조직 전제]
- **저항 요인**: [막는 힘과 그 이유]
- **1차 효과**: [직접적 결과]
- **2차 효과**: [파생 결과]
- **일반화 경계**: [이 사례가 다른 조직에 복제 가능한 정도]
```

### 트랙 `?` — 섹션 생략

트랙이 `?` 이면 delta 섹션을 생략하고, 대신 "이 글이 어느 트랙에 새로 속할 수 있는가"에 대한 간단한 메모만 남긴다:

```
## 트랙 미분류 메모
- 기존 트랙에 안 맞는 이유:
- 잠재 신규 트랙 제안:
```

## 7. 범용 평가 루브릭

분석 노트 작성 후 **5항목 × 1-5점** 으로 자체 평가한다. 기준선 3.5.

| # | 항목 | 기준 | 주의 |
|---|------|------|------|
| 1 | **인사이트 밀도** | 원본을 안 읽어도 핵심을 잡을 수 있는가. 분량 대비 가치. | 길다고 높은 점수 아님 |
| 2 | **계층 자연성** | 원칙/사례/프레임 구분이 억지 없이 떨어지는가 | 경계 모호 시 가이드 §2.5 적용 |
| 3 | **근거 강도** | B/C: 출처·수치·검증이 붙어있는가. A: 논리 일관성이 유지되는가 | A는 N/A 아님 — 논리 평가 |
| 4 | **부가가치** | 단순 요약을 넘어 분석자 시각(비판·확장·반론·맥락)이 더해졌는가 | 원본 복붙형이면 낮음 |
| 5 | **연결 품질** | 관련 노트 연결이 실질적 관계를 갖고 지식 지도로 이어지는가 | "같은 주제"만으로는 낮음 |

평균 3.5 미만이면 보완 후 재평가한다.

### frontmatter에 기록
```yaml
eval_scores:
  인사이트_밀도: 4
  계층_자연성: 4
  근거_강도: 4
  부가가치: 4
  연결_품질: 5
```

### v1 → v2 점수 이월 매핑

기존 v1 노트를 마이그레이션할 때:

| v1 키 | v2 키 | 메모 |
|---|---|---|
| 인사이트_유용성 | 인사이트_밀도 | 그대로 이월 |
| 계층_분류 | 계층_자연성 | 그대로 이월 |
| 근거_충분성 | 근거_강도 | 그대로 이월 (A에서는 N/A 였던 값을 논리 일관성 점수로 재평가 가능) |
| 실행_가능성 | 부가가치 | **느슨한 매핑** — 점수는 그대로 이월하되, 다음 재평가 시 새 기준으로 덮어쓴다 |
| 연결_의미성 | 연결_품질 | 그대로 이월 |
