# 트랙 정의 및 판별 규칙

> analyze-source v2 부터 도입된 "트랙(track)" 차원.
> 깊이(A/B/C)·렌즈(4개)와 **직교**하는 분류이며, 분석 노트가 어떤 관점으로 읽혀야 하는지를 결정한다.

## 트랙 개요

본 레포는 **초기 3개 트랙**으로 시작한다. 어느 트랙에도 자연스럽게 들어가지 않는 글이 2~3건 누적되면 새 트랙을 추가한다 (과적합 방지).

| Track | 한 줄 정의 | 핵심 질문 | 주력 렌즈 기본값 |
|---|---|---|---|
| **`harness`** | AI 작업 환경(에이전트·워크플로우·가드레일·스킬)을 **구축·운영**하는 패턴 | "내 하네스에 어떻게 반영할 것인가?" | technical + process |
| **`model`** | LLM·AI 모델 **그 자체**의 아키텍처·학습·역량·한계 | "이 기술이 모델 역량의 어느 축을 바꾸는가?" | technical + cognitive |
| **`ax`** | AI 전환 — **조직·팀·프로덕트·실무**의 도입과 변화 | "사람·조직이 AI를 어떻게 받아들이나?" | org-culture + process + cognitive |

## 트랙별 상세

### `harness`

**대상 콘텐츠**
- 에이전트 설계/오케스트레이션 패턴
- 스킬·프롬프트·가드레일·훅 등 구체적 기법
- 하네스 운영 경험담·수치
- 개발 워크플로우·CI/CD 자동화·doc-gardening

**시그널 키워드**
`프롬프트`, `가드레일`, `에이전트`, `워크플로우`, `오케스트레이션`, `파이프라인`, `스킬`, `툴 호출`, `컨텍스트 관리`, `AGENTS.md`, `훅`, `MCP`

**분석 포커스**
- 어떤 기법·패턴·수치가 내 하네스에 이식 가능한가
- 저자가 부딪힌 실패와 그 해결책
- 재현 비용 / 확장성 / 경계 조건

### `model`

**대상 콘텐츠**
- LLM 아키텍처 논문 (MoE, 월드 모델, 새 attention 구조 등)
- 학습 방법론 (RLHF, RLVR, GRPO, DPO 등)
- 벤치마크·평가 체계 (ARC-AGI, SWE-bench, MMLU 등)
- 모델 자체의 능력·한계·스케일링 연구
- 모델 아키텍처의 이론적 분석

**시그널 키워드**
`arxiv`, `벤치마크`, `아키텍처`, `파라미터`, `어텐션`, `학습`, `손실`, `강화학습`, `토큰`, `스케일링`, `MoE`, `월드 모델`, `라우터`, `임베딩`

**분석 포커스**
- 이 기법이 **무엇을** 바꾸는가 (능력의 어느 축)
- 선행 연구 대비 기여도와 한계
- 재현 가능성 (공개 코드·체크포인트 여부)
- 벤치마크 일반화 가능성 (단일 벤치마크 편향 여부)

### `ax`

**대상 콘텐츠**
- 조직·팀의 AI 도입 경험 (AX Champions, 채널톡, SOP 경영 등)
- AI가 바꾸는 직무·채용·시장 구조
- 프로덕트 관점의 AI 전환 (SaaS 피벗, 이커머스 영향)
- 개발자·PM 역할 변화, 정체성 담론
- 사회·문화 차원의 AI 시대 논의

**시그널 키워드**
`채용`, `고용`, `조직`, `팀`, `리더십`, `경영`, `시장`, `매출`, `전환`, `도입`, `챔피언`, `CS`, `프로덕트`, `고객`, `사용자 경험`, `정체성`, `역할`, `철학`

**분석 포커스**
- 이 변화가 **성립하는 조건**은 무엇인가 (조직 전제)
- 누구에게 혜택/부담이 가는가 (1·2차 효과)
- 저항 요인·실패 패턴
- 일반화 가능성 (N=1 생존자 편향 경계)

## 트랙 판별 알고리즘

분석 시 아래 순서로 체크한다.

### 1차 판별 — 주력 의도 기반

1. 글의 주된 관심사가 **"에이전트·워크플로우·스킬·가드레일의 설계와 운영"** 인가? → `harness`
2. 글의 주된 관심사가 **"모델·알고리즘·아키텍처 그 자체의 역량과 한계"** 인가? → `model`
3. 글의 주된 관심사가 **"사람·조직·시장이 AI를 어떻게 받아들이는가"** 인가? → `ax`

주력 의도란 "이 글의 **핵심 인사이트가 독자의 어느 영역을 움직이는가**"이다. 키워드가 겹쳐도 주력은 대개 하나로 수렴한다.

### 2차 판별 — 경계 케이스

두 트랙이 비슷하게 강하면 아래 tie-breaker 적용:

| 충돌 | Tie-breaker |
|---|---|
| `harness` vs `model` | 글이 "모델을 바꿔 해결"한다면 `model`, "모델은 두고 환경을 바꿔 해결"한다면 `harness` |
| `harness` vs `ax` | 글이 "1인 개발자가 자기 작업 환경을 어떻게 짜는가"를 다루면 `harness`, "조직이 어떻게 도입하는가"를 다루면 `ax` |
| `model` vs `ax` | 드문 케이스. 글이 "모델 기술의 사회적 영향"에 무게를 두면 `ax`, "기술 자체의 작동"에 무게를 두면 `model` |

### 3차 판별 — 어디에도 안 맞을 때

- 트랙 필드를 **`?`** 로 두고 분석을 진행한다 (디폴트 트랙 강제 금지 — 하네스 편향 재발 방지).
- 사용자에게 "새 트랙 제안이 필요한가?" 확인을 요청한다.
- 동일 패턴의 글이 **2~3건 누적**되면 새 트랙을 설계해 추가한다.

## 트랙 ≠ 태그

- **트랙(track)** 은 **단 하나** 만 고른다. 글의 주력 관점을 결정.
- **태그(tags)** 는 여러 개 가능. 글이 다루는 주제·키워드를 횡단적으로 표시.
- `track: model` 이면서 `tags: [harness, eval, ...]` 인 글은 자연스럽다.
  예: "새 LLM 아키텍처가 하네스 설계에 시사점을 던진다" → 트랙은 `model`, 태그에 `harness` 포함.

## 트랙과 렌즈의 관계

트랙별 **기본 렌즈 조합**은 판별을 돕는 힌트일 뿐, 실제 렌즈 선택은 소스 내용을 보고 독립적으로 한다.

| 트랙 | 권장 렌즈 조합 | 비고 |
|---|---|---|
| `harness` | technical + process | cognitive 부분 추가 가능 |
| `model` | technical + cognitive | process 는 드물게 |
| `ax` | org-culture + process + cognitive | technical 은 부분 적용 |

렌즈는 `analysis_lenses` 필드에서 별도 관리되며 트랙과 무관하게 결정된다.

## 트랙별 검증(B/C 깊이)의 차이

`analysis-guide.md` 의 검증 섹션이 범용이지만, 트랙별로 특히 집중해야 하는 포인트가 있다.

| 트랙 | 우선 검증 대상 |
|---|---|
| `harness` | 제품/도구/스킬의 실존 확인, 저자 신뢰성, 수치의 내부 계산 정합성 |
| `model` | 논문 arXiv ID, 코드 레포 공개 여부, 벤치마크 수치 1차 출처, 선행 연구 비교의 공정성 |
| `ax` | 조직/기업 실재, 사례 대표성(N=1 생존자 편향), 수치 출처(IR/매출/채용 공시) |
