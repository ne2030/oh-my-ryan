# rg-explain-html — 범용 설명 HTML

독자가 처음 접하는 주제를 이해하고 판단할 수 있는 설명 HTML을 만든다. 특정 문서 체계, 용어집, 외부 작성 CLI를 전제하지 않는다. 프로젝트에 별도 문서 작성 규칙(예: Archdoc)이 있고 이 문서의 규칙과 충돌하면 프로젝트 규칙을 우선한다. 다만 어떤 규칙이든 아래 목적을 해치면 따르지 않고 사용자에게 알린다.

## 목적

모든 규칙은 아래 세 가지를 위해 있다.

- **한눈에 들어온다:** 핵심과 큰 그림이 첫 화면에서 보인다. 다 읽지 않아도 무엇을 설명하는 문서인지 안다.
- **흐름이 보인다:** 왜 필요한지, 무엇이 문제인지, 어떻게 풀었는지가 순서대로 이어진다.
- **내용을 이해한다:** 다 읽으면 구조, 이유, 고른 안과 버린 안을 설명할 수 있다.

어떤 규칙을 따른 결과가 이 목적을 해치면, 그 규칙을 따르지 않는다. 그리고 사용자에게 어느 규칙이 어떻게 목적을 해치는지 알린다.

## 0. 시작 전 짧은 인터뷰 (브리프가 불완전할 때)

바로 HTML 작성으로 뛰어들지 말고, 사용자의 요청에 아래 4가지가 이미 명시돼 있는지 먼저 확인한다. **하나라도 비어 있고 추측하면 방향이 크게 갈릴 수 있으면, 작성 전에 2~3개의 짧은 질문으로 먼저 확정한다.** (브리프·원천 문서에 이미 충분하거나, 사용자가 "알아서 바로 만들어 줘"·비대화형 배치 실행을 지시한 경우에는 생략하고 가정한 전제를 첫머리에 짧게 밝힌다.)

1. **독자 수준과 배경**: 처음 접하는 입문자용인지, 실무 개발자·의사결정자용인지
2. **핵심 질문·강조 포인트**: 전체 개요가 중요한지, 특정 비교·실패 사례·선택 기준에 무게를 둘지
3. **시각화·모션 밀도**: 정적 도식 중심인지, **단계별 모션그래픽·시나리오 전환 인터랙티브 SVG**를 적극 넣을지
4. **출력 형태**: 단일 HTML인지, 멀티 페이지/기존 문서 개정인지

## 1. 이해 흐름과 내용 설계

1. **독자·목적·완료 행동**: 먼저 독자가 누구이며, 왜 이 문서를 읽고, 읽은 뒤 무엇을 이해·판단·실행할 수 있어야 하는지 정한다.
2. **도입부와 절별 배경 맥락 선행 (생략 금지)**:
   - 입력 메모나 브리프가 핵심 쟁점만 축약해 놓았더라도, 문서 **도입부(첫 화면)**에서 대상, 목적, 전체 구조를 먼저 보인다. 구성 요소가 셋 이상이면 그림으로 보인다.
   - 각 절의 **첫 문단**은 구체적인 수치·기호(`A`, `B`, `K` 등)부터 던지지 말고, **원래 업무·시스템이 어떻게 동작하는지** 배경을 먼저 설명한 뒤 사례로 들어간다.
   - **원리와 사례 구분**: 제목과 핵심 명제는 특정 사례 하나로 좁히지 말고 일반 원리로 쓰고, 구체적 사례는 그 원리를 보여 주는 예시로 구분한다.
3. **전체와 세부의 위계**:
   - 문서 전체를 안내하는 구성·흐름은 필요한 도입 다음, 개별 주제의 세부 설명보다 앞에 둔다. 한 절만 설명하는 그림은 그 절에 둔다.
   - 글자 크기뿐 아니라 무엇을 포괄하는지와 읽는 순서가 위계를 보여야 한다. 전체 흐름을 여러 절의 그림에서 독자가 다시 조립하게 하거나, 더 좁은 주제의 하위 설명으로 두지 않는다.
   - 도입에서 중요하다고 제시한 문제·이유마다 본문이 필요한 설명·설계·근거를 실제로 제공해야 한다. 상위 설명을 반복하거나 질문을 다시 적은 것을 답으로 세지 않는다. 중요도는 글자 수나 절별 같은 분량으로 판정하지 않고, 독자가 해당 판단을 할 만큼 답했는지로 확인한다.
4. **주제 성격별 절 개요 (HTML 작성 전 선행)**:
   - **배경과 용어·기호**: 처음 나오는 도메인 용어와 기호의 정체·역할
   - **핵심 구조·논리**:
     - 개념·아키텍처 소개라면 **구성요소·역할·동작 흐름**
     - 비교라면 **같은 기준 축 대조** (같은 기준으로 대조하고, 수치·변환·판정에는 출처와 조건을 붙인다)
     - 문제·개선이라면 **동일 사례 관통 흐름**: ① 문제 원리 → ② **문제 사례(Before)**로 무엇이 어떻게 망가지는지 보여 줌 → ③ 원인 파악 → ④ 해결책 제시 → ⑤ **방금 그 같은 사례에 적용했을 때 어떻게 해결되는지(After)** 대조 → ⑥ **실질적 대안이 있을 때만** 대안 비교·선택 이유 (사례를 해결 쪽에만 떼어 놓지 않는다)
     - **허수아비 대안 금지**: 대안 비교는 일반적으로 통용되는 방식이나 트레이드오프가 뚜렷해 실제로 고려할 만한 대등한 선택지가 있을 때만 쓴다. 명백히 결함이 있거나 기존 버그에 불과한 방식을 억지로 대안으로 세워 비교하지 않으며, 실질적 대안이 없으면 비교를 생략한다.
   - **미확정 사항·경계**: 가설, 미결정, 기존 결정 같은 예외에만 그 자리에 상태 표시를 붙인다. 누가 무엇을 확정해야 하는지 직접 적는다.
   - **문서 크기에 맞추기**: 작은 주제에 정상과 실패용 절을 따로 두거나 그림 수를 강제하지 않는다. 고정 템플릿 대신 내용의 관계에 맞는 형식을 고른다.
5. **절 이름과 제목 단계**:
   - **목차만 읽어도 문서의 흐름과 큰 그림이 이해되게** 절 이름을 짓는다. 제목을 구체화해도 절이 답하는 질문은 유지한다. 문제 절에는 확인된 불편, 기능 절에는 사용자가 하는 일, 결정 절에는 선택한 대상을 이름 붙인다. 해결책 이름을 문제 제목으로 쓰거나 제목을 위해 미확인 문제를 발명하지 않는다. 구체적인 사실만 늘어놓으면 목록처럼 보이므로, 묶는 말이 필요하면 역할과 내용을 함께 쓴다.
   - 절은 `<h2>`, 하위 절은 `<h3>`, 그 안의 항목 제목은 `<h4>`다. 목차 단계와 제목 단계를 맞춘다. 본문에서 다른 부분을 가리킬 때는 번호 대신 이름을 쓴다.

## 2. 형식과 말

- **글은 꼭 필요할 때만**: 문장과 문단은 글로만 설명할 수 있는 것(얽힌 인과, 이유, 조건)에만 쓴다. 단, 도식을 넣었다는 이유로 본문 해설(`p`)을 2~3문장으로 축약하지 말고, 독자가 배경과 이유를 온전히 이해할 수 있을 만큼 충분히(보통 2~4문단) 풀어쓴다.
- **표·카드·목록의 간결함**: 표·카드·목록은 짧은 구로 뜻이 충분하면 구로 쓴다. 머리말이 주체·대상을 이미 밝힌 경우 ‘확인한다·저장한다·거절한다’를 ‘확인·저장·거절’로 정리한다. 어미만 지운 긴 나열은 교정으로 보지 않으며, 필요한 조건과 인과가 모호해질 때만 문장을 유지한다.
- **관계에 맞는 나열 모양 선택**: 한 문서 안에서 한 모양(굵은 이름 아래 들여 쓴 설명)만 반복하지 않는다.
  - 문서나 절의 머리 정보(문제, 목표, 범위): 라벨 칸 판(`facts`)
  - 같은 수준의 독립 항목을 제목 단위로 훑거나 선택: 카드(`cards`). 같은 카드 모양은 항목들이 동등한 묶음이라는 뜻이므로 비교 기준과 제목의 수준을 맞춘다. 순서·인과를 보여야 하면 흐름 표현을, 같은 속성을 정밀 비교하면 표를, 짧은 나열이면 목록을 쓴다. 글이 길다는 이유만으로 카드로 나누지 않는다.
  - 대비되는 둘: 두 칸(`pair`)
  - 순서가 있는 단계: 번호 단계(`steps`)
  - 같은 속성 여럿을 비교: 표 (**단, 표는 기준표·상태표·이슈 목록처럼 짧은 값 대조에만 쓴다. 작동 방식·판단 경로·사례별 분기 차이처럼 '어디서 어떻게 갈리는지'가 핵심인 절을 표로 대체하지 않으며, 표 셀 안에 2문장 이상의 인과·이유 설명을 넣지 않는다.**)
  - 용어 풀이: 이름과 설명 목록(`defs`)
- **문단·셀의 분량 제한**: 화면에서 3줄을 넘는 문단(본문 `<p>` 및 표·카드·목록 셀 모두)은 나눈다. 나누기 어려우면 구조로 바꾼다. (한 문단을 짧게 나누라는 뜻이지 절 전체의 배경·원인 설명을 생략하라는 뜻이 아니다.) 문단을 목록으로 옮길 때는 읽을 양도 함께 줄인다. 문장 하나를 항목 열 개로 쪼개지 않으며, 한 카드·섹션에 평면 불릿 5개 이상을 나열하지 않는다(5개를 넘기면 의미 단위로 2~3개 그룹·단계 게이트·매트릭스로 묶는다).
- **접기·예시·위계**: 같은 형식이 반복되는 긴 상세는 접기(`<details>`)로 두고, 접힌 줄에 이름과 핵심 결론을 쓴다. 예시는 설명 문장과 섞지 않고 다음 줄에 작은 회색 글씨로 둔다. 절 제목, 소제목, 본문 사이의 글자 크기 차이가 화면에서 구분되어야 하며 소제목 아래 정의 목록은 들여 쓴다.
- **본문 텍스트 구조화 (민무늬·동일 소제목 반복 금지)**: 도식 아래에 소제목 없이 `<p>` 문단만 줄줄이 붙이지 않으며, 반대로 모든 절에서 똑같은 색·무게의 `<h3>` 소제목 5~6개를 수직으로 똑같이 반복해 글 벽처럼 만들지도 않는다.
  - **전후 대비(`Before vs After`, `문제·원인 vs 해결`)**처럼 대비되는 둘은 2열 대비(`pair`)와 의미 색(문제·원인=붉은/주황 톤, 해결·결과=초록/파랑 톤)으로 공간·색상 위계를 나눈다.
  - **대안 비교는 표·정렬 블록으로**: 대안을 줄글 한 문단에 뭉뚱그려 쓰지 않는다. 실질적 대안이 있을 때는 **비교 표(`방식 | 장점 | 한계·부담 | 선택`)** 또는 같은 축이 정렬된 비교 블록으로 분리한다.
- **말의 정확성**:
  - 개념은 먼저 무엇인지 소개하고, 그 뒤에 특성과 이유를 쓴다.
  - 무엇이 무엇을 어떤 조건에서 하는지 쓴다. 공간·운동 은유 동사로 관계를 대신하지 않는다.
  - **긍정형 서술 · 면책 문구 금지**: 긍정형으로 쓴다. 부정문은 꼭 지켜야 할 경계, 사용자가 명시적으로 강조한 제한, 생략하면 포함되는 것으로 오해할 가능성이 높은 경우처럼 강한 이유가 있을 때만 쓴다. 그 이유가 없는 ‘하지 않는다’는 제거하고, 책임 범위는 가능하면 실제 담당 주체와 동작으로 표현한다. **독자가 가정하지 않은 전제를 반박하지 않으며**, *"이 사실만으로 ~가 확정되는 것은 아니다"*, *"~다른 조건까지 대신 판단하지는 않는다"*, *"~상황에 따라 달라진다"*, *"이 문서는 구체적인 결론을 정하지 않는다"* 같은 방어적 꼬리말을 붙이지 않는다. 확정된 적용 제외·증거의 한계·관측과 가정의 구분은 필요한 경계로 직접 적고, 미확정 사항은 무엇이 비어 있고 누가 확정해야 하는지 밝힌다.
  - 대상이 상위 목적의 어느 필요에서 나왔는지 쓴다. 효익(예: 재사용)을 목적으로 바꿔 쓰지 않는다.
  - 같은 말을 두 범위로 쓰지 않는다. 전체와 그 부분이 같은 이름을 쓰게 되면 한쪽에 다른 이름을 붙인다.
  - 이름과 제목은 대상·역할·내용을 정확하게 전달해야 한다. 이름만 읽고 예상한 대상과 실제 본문·동작이 일치하는지 확인한다. 입력·산출물 중 하나로 이름을 짓는 고정 공식을 적용하지 않는다.
  - 이름과 제목은 짧고 뜻이 통하게 쓴다. 제목은 명사형으로 쓰고, 질문형이나 장면 제목은 쓰지 않는다.
  - 피드백에 반응해서 목적 없는 안내 문장을 덧붙이지 않는다.

## 3. 그림과 시각화 구현 (`rg-visual-explainer` 모듈 위임)

- **시각화 모듈 위임 (필수)**: 문서의 모든 도식·인라인 `<svg>`·작동 원리 시각화 설계와 렌더 검수는 **`rg-visual-explainer` 모듈(`../rg-visual-explainer/core.md`, `../rg-visual-explainer/references/visual-gate.md`)을 단일 원본으로 따른다.**
  - 도형을 그리기 전에 `<svg>` 안의 `<desc>` 태그에 독자의 눈에 보일 **구체적 장면·미니 화면·데이터 구조·기하 축 콘티**를 먼저 설계한다.
  - 정해진 차트 템플릿이나 천편일률적인 `A → B → C` 텍스트 박스 흐름도로 때우지 않는다. 특히 **CSS `<div>`/`<span>` 테두리 박스와 일반 텍스트 `→` 화살표로 도식을 대체하는 것(인라인 `<svg>` 0개)**은 금지한다. 인터랙티브 단계 전환이 필요하더라도 **실제 인라인 `<svg>` 도식 위에** 상태 강조·탈락 표시를 얹는 방식(Static-First)으로 구현한다.
  - SVG 내부에는 서술형 문장을 넣지 않고 짧은 명사구·실제 값·기호만 두며, 인과 서술은 HTML `<p>`/`<figcaption>`이 담당한다.
- **시각 패턴 참고**: 사용자가 명시적으로 지정한 참고 HTML/CSS가 있으면 그 원문을 우선으로 참고한다. 지정한 참고가 없을 때는 `node <skill-root>/scripts/read-patterns.mjs --list` (저장소 시험 시 `node skills/rg-explain-html/scripts/read-patterns.mjs --list`)로 공통 디자인 규칙과 패턴 목록을 먼저 읽고, 필요한 패턴만 `--ids id[,id...]`로 꺼내 참고한다. 기존 `assets/presentation-reference.html`은 사용자가 명시한 경우에만 사용한다.
- **그림의 선택과 텍스트 박싱·표 남용 금지**: 설명할 것이 복잡하거나 여러 개이고, 그림이 전체 흐름이나 구성을 설명하는 데 도움이 되면 그림으로 보인다. 요소가 셋 이상 연결되거나 흐름이 있으면 먼저 그림을 검토한다. 글로 이미 적었거나 예시 그림이 있어도, 전체 구성을 보이는 그림이 도움이 되면 함께 둔다. 구성 그림은 SVG로 그리고, 대표 흐름을 그 그림 위에서 보인다. 글 상자 나열이나 관계 표로 그림을 대신하지 않는다.
  - **도입부 SVG 1개 + 본문 표 도배 금지**: 문서 전체에 그림이 도입부 1개뿐이고 본문 2개 이상 절이 연속으로 `<table>`로만 채워졌다면 시각화가 빠진 신호다. 도입 그림 외에도 **메커니즘·방식 비교(판단 주체·시점 차이)**, **사례별 분기·흔들림 경로**, **선택 기준·경계**가 핵심인 절에는 각 절의 구조를 직접 보여 주는 SVG 도식을 두고, 표는 짧은 판정·요약으로만 보조한다.
  - **도식 안의 설명 문장을 지우고 도형·선·위치·크기·기준선만 남겼을 때도 핵심 구조가 읽혀야** 시각화다. 문제·오판·경계가 있는 주제라면 단순히 입력 숫자만 찍어두지 말고 기존 방식이 어디서 잘못된 결론으로 빠지는지 vs 바른 판단 경로까지 도식 안에서 보이게 그린다.
  - **수치·한도·경계 비교** → 기준선(Threshold) 위 막대·점 위치 차트 / **포함·상하위 계층** → 중첩 도형·트리 + 허용/차단 방향 화살표 / **분기·조건 게이트** → `<svg>` 경로 / **상태 전이·단계 경계** → 단계 노드 + 전이 화살표 / **허용과 차단·원칙과 예외** → 한 도식 안에 허용(실선·긍정 색)과 차단(점선·부정 색·✕)을 나란히 그린다.
  - 칸마다 글이 두 줄 이상인 목록형 그림은 HTML로 만든다.
  - 도식에 이미 그린 노드 이름을 바로 아래 2열 카드나 목록으로 말만 바꿔 되풀이하지 않는다.
- **시각적 무게 차등·의미 색·한글 타이포그래피·안티패턴 금지**:
  - 권고안·핵심 결론은 면배경·테두리·크기로 주연 처리하고, 기각안·부수 정보는 톤 다운·축소한다. 비교 대상은 동일한 비교 축으로 정렬한다. 상태·판정·찬반·결함이 있는 문서는 2~3개의 제한된 의미 색(배지·칩·도트·면배경)으로 구분한다.
  - **한글 줄바꿈 기본값**: 한글 본문·카드·표·캡션에는 `word-break: keep-all; overflow-wrap: break-word;`를 적용해 단어 중간 끊김을 막는다.
  - **좌측 컬러 띠 카드(Stripe Card) 및 대량 카드 도배 금지**: 카드 왼쪽 테두리에 두꺼운 색 띠(`border-left` 액센트)를 두른 띠 카드 디자인을 쓰지 않는다. 10개 이상의 동종 항목을 같은 모양의 카드 그리드로 나열하지 말고, 집계·유형별 그룹·컴팩트한 표(테이블)로 압축한 뒤 대표 사례 3~5개만 발췌하거나 접힌 상세로 둔다.
  - 여러 열을 비교하는 도식은 거대한 통 SVG 하나로 축소하지 말고 열별 개별 SVG로 나누어 좁은 화면에서도 글자 크기를 지킨다.

## 4. 문서 규모별 탐색·분할 기준

- **작은 설명** (섹션 1~5개 & 주요 시각 블록 7개 이하): 단일 페이지(필요 시 상단 칩 목차).
- **긴 단일 주제** (섹션 6개 이상 **또는** 주요 시각 블록 8개 이상 / 예상 스크롤 4화면 초과): **좌측 고정(Sticky) 사이드바 목차**와 현재 위치 하이라이트를 두고, 목차는 2단계(`h2` > `h3`)까지 쓴다(좁은 화면에서는 상단 접이식 바로 전환). 한 섹션 내부에 또 세로 좌측 탭을 중첩해 본문 폭을 좁히지 않는다.
- **거대한 복합 주제** (시각 블록 약 15개 이상이거나, 독자·층위가 갈리거나, 독립 대상·케이스가 4개 이상이고 각 2개 이상의 도식·표가 붙을 때): `index.html` 허브 + 하위 페이지의 **멀티 페이지**로 나눈다. 단일 독립 HTML 1개를 요청받았다면 파일 분리 대신 상단 탭 뷰로 화면을 나눈다.

## 5. 내용 정확성·기존 문서 개선·보이기 전 확인

1. **내용 정확성과 근거 대조**:
   - 모든 설명과 시각화는 상위 목적·근거 자료·실제 동작과 일관되어야 한다. 검증 책임·시험 조건·채택 및 실패 조건·기존 차단 조건을 다루는 주제라면 작성 전에 해당 조건을 찾아 작성 뒤 실제 답하는 본문 위치와 대조한다. '기준을 유지한다'는 선언만으로 구체적인 시험이나 실패 처리를 대신하지 않는다. 참조 자료가 부족하다는 이유로 기존 조건을 완화하지 않으며, 유지한 조건과 확인하지 못한 근거를 구분한다.
   - 기존 설계나 설명을 뺄 때는 그것이 왜 있었는지 먼저 확인한다. 기존 초안에서 가져온 구분은 예를 들어 성립하는지 따져 보고, 새로 넣은 설명·해석마다 반례를 찾아본다.
   - 예시는 문서의 설명대로 끝까지 옮길 수 있어야 하며, 한쪽 경우만 치우치지 않고 여러 경우를 고르게 보인다.
2. **기존 HTML 문서 개선 시**: 기존 CSS·카드 구조·산문 문자열을 그대로 재사용해 겉만 패치하지 말고, 원천 사실만 분해해 백지에서 새 구조로 다시 설계한다. 동시에 유효한 설명의 역할(전체를 안내하는 그림, 판단에 필요한 비교·사례, 근거 연결)이 수정 뒤에도 같은 판단을 돕는지 이전 판본과 대조한다. 삭제·이동·대체한 핵심 설명은 새 위치와 역할, 바꾼 이유를 작성·검토 기록에 남기고, 낡거나 틀린 설명은 근거에 맞게 고치거나 제거하며 중복은 통합한다. 원본의 모양·그림 수를 고정하는 규칙으로 쓰지 않는다.
3. **예시와 그림 정합성 검증**: 대표 사례와 실패·수정 사례를 본문과 그림에서 각각 따라가며, 같은 입력이 같은 조건을 거쳐 같은 결과에 도달하는지 확인한다. 그림의 모든 화살표가 가리키는 실제 끝점과 범례를 대조하고, 본문이 요구한 단계를 건너뛰는 경로가 있으면 고친다. 목차·그림의 표지도 본문과 같은 작성 언어와 용어를 사용했는지 확인한다.
4. **독립 검수(`references/quality-gate.md` + `../rg-visual-explainer/references/visual-gate.md`) 및 렌더 확인**: 초안 생성 직후 바로 내보내지 말고, 먼저 `node <skill-root>/scripts/check-html.mjs <생성된_HTML_경로>`로 구조·SVG 하드 게이트를 통과시킨 뒤 `references/quality-gate.md`와 `../rg-visual-explainer/references/visual-gate.md` 기준을 하나씩 대조해 검수한다. 브라우저 실행이 가능한 환경에서는 렌더한 화면을 스크린샷으로 찍어 첫 화면과 모든 절의 정보 관계·넘침·도식 글자 크기·충돌 0건을 이미지로 확인한다. 하나라도 결함이 있으면 수정하고 영향을 받은 화면을 다시 확인한 뒤 보고한다.
5. **메타·추적 로그 (선택)**: 생성한 HTML(멀티 페이지는 허브 `index.html`)의 `<head>`에 `<script type="application/json" id="doc-meta">{"skill":"rg-explain-html","layout":"single|single-toc|sidebar-toc|multipage|tabs","generated_at":"...","sources":[...]}</script>`를 넣는다. 로컬 환경에 별도 실행 로거가 설정돼 있으면 저장 직후 실행하고, 없으면 생략한다.
6. **보고 형식**: 결과 파일과 함께 확인한 스크린샷(렌더 가능한 환경인 경우)과 자체 비평(잘된 점, 남은 문제와 원인, 새로 넣은 해석, 하지 않은 검증)을 구분해 함께 보인다.
